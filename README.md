# ContractLens

**ContractLens** reads a contract or Terms & Conditions document, splits it into individual clauses, classifies each one, flags clauses that look unusually risky compared to typical/baseline contract language, and rewrites the flagged ones in plain English so you can actually understand what you're agreeing to before you click "I Agree."

## Why this is useful

Nobody reads Terms & Conditions. They're long, written in dense legal language, and the clauses that actually matter to you (can I cancel? does this auto-renew? who owns my data? what happens if something goes wrong?) are buried in paragraphs of boilerplate. ContractLens automates the first pass a careful reader would do: find the clauses that touch on fees, cancellation, auto-renewal, data sharing, liability, and dispute resolution, and call out the ones that deviate from what's normal.

## How it works

1. **Segmentation** (`src/segmenter.py`) uses spaCy to split raw text into individual clauses, cleaning up numbered-list artifacts along the way.
2. **Classification** (`src/classifier.py`, `src/train_classifier.py`) uses a TF-IDF + logistic regression model, trained on a hand-labeled dataset of ~90 example clauses (`data/clauses_dataset.csv`), to predict which of 7 categories each clause belongs to: fees, auto-renewal, cancellation, data sharing, liability, dispute resolution, other.
3. **Red-flag scoring** (`src/red_flags.py`) a rule-based engine checks each clause against category-specific criteria for what's "normal" (e.g. a 30-day cancellation window is typical; a 3-day window or "no cancellations" is flagged). Each flag carries a plain-language reason and a severity. Flag severities are summed into an overall 0–100 document score.
4. **Plain-English rewriting** (`src/plain_english.py`) flagged clauses are summarized with Sumy (LexRank) to trim boilerplate, then combined with a category-specific explainer template so you get a short, plain-language description of what the clause means and why it was flagged.
5. **Interface** (`app.py` + `templates/`, `static/`) is a Flask app with a JSON API (`POST /analyze`) that runs the pipeline and a plain HTML/CSS/JS frontend that lets users paste or upload a document, sends it to that endpoint, and renders the overall score plus an expandable clause-by-clause breakdown.

## Design decisions

**Why rule-based red-flag scoring instead of a black-box "risk" model?**
Deciding whether a clause is risky is a *policy* decision, not a pattern-recognition problem. For example, "a cancellation window under 14 days is a flag" is a threshold someone chose on purpose, not something you'd want a model to infer implicitly from limited data. Rules keep that policy explicit, readable, and easy to adjust (change a number, add a phrase) without retraining anything. They also mean every flag comes with a human-readable reason instead of an opaque score, which is important for a tool whose whole point is transparency.

**Why TF-IDF + logistic regression instead of a transformer model for classification?**
With only ~90 labeled training examples, a large pretrained language model would be overkill: slower, harder to explain, and not meaningfully more accurate on a dataset this small. TF-IDF + logistic regression is fast to train, easy to inspect, and a well-established baseline for small text classification tasks like this one.

**Why Sumy for summarization instead of an LLM?**
Sumy's LexRank algorithm is lightweight, runs locally with no API calls or cost, and is good enough at trimming a long clause down to its most central sentence(s), which is really all that's needed here, since the category templates (not the summarizer) do the job of translating legal phrasing into plain language.

**Why Flask + plain HTML/CSS/JS instead of Streamlit?**
Streamlit is faster to prototype with, but it owns the entire page - you write Python widgets, not markup, and get Streamlit's default look with limited styling control. Flask serving a real HTML/CSS/JS frontend means a proper separation between the pipeline (an API) and the interface (a page that calls it), full control over layout and styling, and a JS layer (`static/js/app.js`) that's a closer match to how a production frontend is actually built.

## Running it locally

```bash
# 1. Create a virtual environment
python -m venv venv

# 2. Activate it (pick the line for your shell)
venv\Scripts\activate.bat     # Windows cmd.exe
venv\Scripts\Activate.ps1     # Windows PowerShell
source venv/Scripts/activate  # Git Bash on Windows
# source venv/bin/activate    # macOS/Linux

# 3. Install dependencies
pip install -r requirements.txt

# 4. Download the spaCy English model and NLTK tokenizer data (one-time setup)
python -m spacy download en_core_web_sm
python -c "import nltk; nltk.download('punkt', download_dir='nltk_data'); nltk.download('punkt_tab', download_dir='nltk_data')"

# 5. Train the classifier (creates the files in models/)
python src/train_classifier.py

# 6. Run the app
python app.py
```

If `python -m spacy download en_core_web_sm` fails with "No package installer found" (can happen with some Python installs), install the model directly instead:
```bash
pip install "https://github.com/explosion/spacy-models/releases/download/en_core_web_sm-3.8.0/en_core_web_sm-3.8.0-py3-none-any.whl"
```

Then open **http://localhost:3000** in your browser, paste in a contract or Terms & Conditions document (or upload a `.txt` file), and click **Analyze document**.

## Limitations / honest caveats

- The training dataset is small (~90 hand-written examples), so classification accuracy on real-world contracts, especially unusual phrasing, won't be perfect. It's a portfolio-grade baseline, not a production legal tool.
- **Scope leans consumer Terms of Service**, not general-purpose contracts. Most examples cover subscription/SaaS-style language (cancellation, auto-renewal, data sharing, arbitration). A few loan/finance-agreement examples were added to help with that domain, but other contract types (employment, real estate, NDAs, etc.) will likely get low-confidence or mislabeled categories, since the classifier has never seen that vocabulary.
- The red-flag rules are a starting policy based on commonly cited norms (e.g. 30-day cancellation/renewal notice windows), not legal advice, and don't account for jurisdiction-specific law. They also rely on specific keyword/phrase matching, so differently-worded clauses that mean the same thing can slip through unflagged.
- **Negation isn't generally handled.** A couple of specific cases are patched (e.g. "we do *not* sell your data" no longer triggers the data-selling flag), but the rules don't actually parse sentence structure - a keyword match next to a "not"/"no" elsewhere in the clause can still misfire in cases not explicitly guarded against. Real negation handling would need actual parsing, not keyword rules.
- **"Plain English" is extractive, not a true paraphrase.** Sumy trims a clause down to its most central sentence(s) - it doesn't rewrite conditionals into natural phrasing (e.g. turning "unless X, Y shall occur" into "if you don't do X, Y happens"). The category explainer and flag reason add context around the original wording, but the clause text itself stays close to the original legal phrasing. Genuine rewriting would need an LLM, which was deliberately left out (see design decisions above) in favor of staying simple, local, and free to run.
- This tool is meant to help a reader triage which clauses deserve closer attention; it is **not** a substitute for reading the actual document or consulting a lawyer for anything that matters.
